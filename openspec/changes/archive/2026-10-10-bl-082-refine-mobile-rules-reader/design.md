## Context

BL-082 is the leading P0 in [the backlog](../../../../docs/backlog.md), ahead of system expansion. It supports the [author vision](../../../../docs/vision/author-desires.md) of quick, mobile-first reference lookup without turning the app into a rules compendium. The [existing viewer ADR](../../../../docs/decisions/2026-08-30-control-self-hosted-pdf-navigation.md) owns the app-controlled viewer, desktop resizing, source rights, and draft-preserving return boundary.

Initial inspection found (the pre-change baseline):

- `ReferencePdfViewer.svelte` places Find below an initially expanded curated outline in a bounded scrolling pane. Compactness is selected by window width, even when the actual reader is a narrow desktop panel or annotation dialog.
- `SheetReferenceController.svelte` provides a full-screen phone surface but uses an aside rather than a modal focus owner. Annotation hosts already own a `DialogShell`; their reader wrappers impose `64dvh` within that shell.
- `PdfPage.svelte` catches page/text errors locally. The parent's actionable fallback and existing negative E2E test handle initialization errors, not those later failures.
- The [BL-084 verification record](../2026-09-12-bl-084-harden-core-mobile-viability/verify.md) records owner approval of closed-tab/saturated-sheet containment fixes. Those are regression checks, not presumed active defects. The physical-phone page error remained unresolved.

There is no new schema or character persistence. Compatibility and layout share an output proof but must remain independently diagnosable.

## Goals / Non-Goals

**Goals:** Resolve or explicitly classify the reported phone compatibility failure, make Find immediately discoverable, preserve usable document space, and provide one reader interaction grammar across sheet and annotation contexts.

**Non-goals:** See [proposal.md](proposal.md). In particular, no PDF engine replacement, highlighting within PDF content, new source rights, generic provider layer, desktop docking redesign, or scroll-direction auto-hide. Highlighted Find result previews are included in the owner-approved proof refinement.

## Decisions

### 1. Diagnose compatibility before choosing a workaround

The pinned modern PDF.js build calls `for await` on the stream returned by `streamTextContent()`. Both page text layers and document Find call `getTextContent()`. This is a credible explanation for the reported `readableStream` error, not a confirmed physical-device diagnosis. WebKit documents stream async iteration arriving in [Safari 26.4](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/#readablestream-async-iteration); PDF.js's [current support guidance](https://github.com/mozilla/pdf.js/wiki/Frequently-Asked-Questions#which-browsersenvironments-are-supported) distinguishes modern and legacy builds and lists Safari under legacy. Current upstream guidance is not proof of the pinned version's support floor. The installed legacy build also contains the iteration call, so merely changing imports is not established as sufficient.

Owner clarification on 2026-10-04 identifies an iPhone 16 Pro Max running reported iOS 26.6.2, using the LAN development server and saturated 2014 character. Safari, Firefox, and Chrome on that same phone show visible PDF content plus the page error; Find fails and can appear stuck at `Searching page 6 of 403...`. All three desktop browsers work according to the owner. This is a phone-environment/text-processing investigation, not an established Safari-brand-only defect or three independent engine reproductions. The reported OS version is newer than the cited feature release, so do not assume an old-browser API gap; verify actual capability, served assets, and failure stage. [verify.md](verify.md) preserves the exact observations and remaining unknowns.

During apply, inspect runtime capability presence, deployed build/worker identities, and the failure stage; do not ask the owner to repeat the baseline merely to begin. Use a controlled missing-capability browser fixture to test the hypothesis, not to claim complete older-Safari emulation. Verify page paint, selectable text, and Find independently. A visible page wrapper or painted canvas alone is insufficient evidence that the complete reader works.

Evaluate the pinned engine's supported compatibility build and matching worker first. Prefer one verified build path serving the agreed supported browsers over user-agent sniffing or two untested bundles. If insufficient, evaluate a bounded compatibility adaptation at the existing PDF boundary; avoid a custom global stream shim or disabling all text support without explicit trade-off review. A changed package/version must be justified, exactly pinned, and verified through dependency gates. Replacing the engine or materially raising the support floor requires owner direction and artifact reconciliation.

The owner accepted working in-app reading and Find on their reported phone plus current stable iOS/Safari and Android/Chrome as required. Record the concrete OS/browser versions verified at implementation handoff rather than claiming every future release is proven. Include physical-phone coverage and regression checks in all three reported iPhone browser apps; record unavailable device coverage explicitly. Preserve older-version compatibility where practical, but the oldest supported version remains evidence-driven, not a promise to support every phone. Fallback is recovery, not success for the required targets. Any reduction of that baseline requires an explicit scope/support decision from the owner, not an inferred exception at a test gate.

**Pre-gate implementation evidence (2026-10-04):** Controlled removal of stream async iteration reproduces the exact reported error with both pinned modern and legacy module/worker pairs. Keep the existing modern build and version, and consume the public `streamTextContent()` reader through the bounded `readPdfText` helper shared by page text and Find. Preserve the engine's chunk item/style/language aggregation; do not patch globals or engine internals. Cancellation must pass an `Error` reason because the pinned transport requires it before marking its controller closed. The targeted WebKit text/Find test passes; physical iPhone diagnosis and supported-version certification remain open. See [verify.md](verify.md) for failed experiments, passing evidence, and the original reproduction.

### 2. Persistent compact controls, with one working area

Use a compact persistent header/control area rather than controls that disappear when scrolling. A first proof can use two short rows, preserving touch targets and readable labels:

```text
Back / Close       Source title       More
Find               Outline            8 / 403
---------------------------------------------
Document OR Find/results OR Outline OR Page tools
```

The layout is illustrative; exact grouping and threshold are proof decisions. Source/version and return context remain identifiable. Find and Outline have direct labeled actions. Page position opens page input and Previous/Next. Resource browsing, where supplied by the host, and the normal browser-opening action move behind an explicitly named secondary control. Failure states also expose browser fallback directly. Browser opening uses the current verified page when available, otherwise the verified starting/general locator; stale locators never regain trust through this shortcut.

In compact presentation, opening Find/Outline/Page tools temporarily uses the document content area, with a visible `Back to document` action. Find receives deliberate focus from its trigger; merely opening the reader must not summon the phone keyboard. Selecting a result or outline/page destination returns to the document, aligns the destination, and moves focus to its named reading region without leaving focus hidden in the tool. Dismissing tools without navigating restores the prior reading position and focus to the tool's trigger. Preserve query, available results, and tool scroll position for the same open document; reset them when changing document or closing the reader. Errors, pending work, and partial search results must not masquerade as completed results. Do not add browser-history entries for individual tool disclosures.

Expanded presentation retains the desktop side-by-side resizable navigation and document. Find precedes the curated outline, with the lower-value native outline initially collapsed. No need to force the compact mode's temporary replacement behavior onto roomy desktop readers.

**Owner-approved proof refinement (2026-10-04):** Keep the search input and status outside a native results disclosure labeled with matching-page count. A newly submitted search expands results once; subsequent progress does not override manual collapse. Preserve that disclosure state through tool transitions and mark each matched portion of the contextual preview using escaped text and semantic `mark` elements, never injected HTML. Match and slice the same NFKC-normalized display text using literal, Unicode-aware case-insensitive matching so normalization does not displace highlight offsets. Retain segments with their search result rather than deriving highlights from an edited, unsubmitted input. This does not change or highlight the PDF text layer. A pure preview projection owns matching/counts/excerpts, with Unicode, metacharacter, and bounded-context tests.

In expanded readers, move the existing page-controls snippet above the PDF region, outside the scrolling navigation pane. The persistent page-position action focuses those controls; narrow readers still disclose the same controls in their dedicated Page tool. Keep the document mounted across width changes and preserve page/search state. Reuse the existing stories and in-sheet proof; in-PDF highlighting stays in the existing backlog exploration, not this change.

### 3. Available-space responsiveness and clear host ownership

**Proof correction (2026-10-07):** Secondary actions use the established `MenuButton` popover and `MenuItemButton` command/link rendering, not a local `<details>` dropdown. Native disclosure was the wrong behavior for an overlay action menu: it supplied no light dismissal and bypassed shared sizing. Extend the shared menu item with native link semantics for browser opening, preserving new-tab/link behavior and closing the popover before commands. Keep native details for inline result/outline disclosure. The Outline shortcut explicitly opens its disclosure and scrolls only the navigation viewport to its heading, then focuses the summary. Compact tool panels grow with content up to the available working-area height; long lists retain bounded scrolling and overflow cues. The hidden document stays mounted at its existing size, avoiding canvas rescaling and reading-position loss when tools grow.

Choose compact controls from the reader's available inline space, initially trialing a threshold around 48rem and refining it during the human proof. This is an implementation starting point, not a normative breakpoint. The existing outer full-screen phone versus desktop side-panel contract remains; inner control layout must also work when a narrow panel sits in a wide viewport. Use container sizing with stable transitions rather than device names. On transitions preserve document/search state and move focus only if the previously focused control becomes hidden.

Allocate the remaining host height to the reader instead of stacking an arbitrary `64dvh` reader inside a full-height dialog. Test safe areas, browser chrome, large text, portrait/landscape, and the virtual keyboard. The active document or tools region owns scrolling; reuse the existing scroll-affordance attachment for bounded text/results. Do not introduce another competing PDF scroll owner or replace page-window virtualization.

`SheetReferenceController` remains responsible for sheet history, invocation focus, and dismissal. Its phone full-screen state needs one accessible focus owner and an inert obscured sheet; reuse/extend `DialogShell` where it fits without remounting character state or resetting the PDF across a breakpoint. Desktop remains non-modal. Annotation hosts keep their existing modal and change its content step rather than opening a nested modal. Reader controls request return from their host; they must not directly commit or cancel drafts. Preserve current sheet browser-Back dismissal, direct-locator behavior, and editor Back semantics.

**Desktop scroll-lock correction (2026-10-07):** The shared global rule previously selected every `dialog[open]`. With the new non-modal desktop reader, that both disabled sheet scrolling and gave sticky sheet navigation an unintended overflow ancestor. Lock the document only while `dialog:modal` exists, including when a real editor is opened over the non-modal reader. Keep the existing phone modality and desktop resize behavior. The regression opens Rules after a sheet-landmark jump, checks stable outline geometry, resizes and scrolls the sheet independently, navigates PDF pages without moving the sheet, and verifies a real note dialog still locks the background. Resume-after-close is a separate proposal captured in the backlog; current close still releases the reader and its transient search state.

**History corrections (2026-10-08):** PDF page jumps are already viewer-local. The first regression came from sheet landmark navigation pushing copies of the open-reader state, causing Close's Back operation to land on another open reader. Centralize sheet/reference history writes in `sheetReferenceNavigation`: push the first sheet-invoked reader, replace subsequent sheet fragments and source choices while it is open, and preserve the original invocation origin/focus owner. Closed-reader landmark navigation still pushes normal history. Directly linked readers have no invented sheet-open entry.

Owner follow-up clarified that explicit Close must not undo background sheet navigation: Quick Reference → open Rules → Inventory → Close must leave Inventory in place. Close, resize dismissal, and the shell's cancellation callback now clear reader state by replacing the current entry at its complete current URL, including the live fragment. Do not call Back, synthesize popstate, or restore a saved opening scroll offset. Restore invoker focus with `preventScroll`; release the viewer as before. Browser Back remains a separate navigation operation, dismissing the single open-reader entry to its pre-reader context; Forward can revisit that entry only if it was left through Back rather than explicitly closed. Repeated open/Close without sheet movement can leave same-URL closed history entries; accept that small native-history trade-off instead of introducing traversal-and-restoration races or private router indexes. Individual sheet jumps during an open reader remain coalesced. Verify URL, exact sheet scroll position, offscreen-invoker focus, resize dismissal, and closed-reader Back/Forward in the actual sheet, not a standalone viewer story.

### 4. Make page and text failures recoverable

Keep initialization, page-render, text-extraction, and Find failure states distinct. Propagate enough status from a failed page/text operation to show a readable explanation and a direct browser fallback near the affected content. A useful painted page can remain available after a text failure, but clearly identify unavailable text selection/Find; do not claim a supported full-reader result. Scope text degradation to known affected operations rather than unnecessarily disabling working pages or every search.

Use bounded explicit retry where meaningful, not automatic reload loops. Rendering cancellation during scrolling/resizing is normal lifecycle behavior, not an error. Abort or invalidate stale load/search results when requests are superseded or the document closes; do not let hidden tools recreate dead workers. Keep the current bounded page render window, clean up resources, and ensure a slow PDF cannot block Close/Back. Returning and fallback never mutate character or annotation data.

The search-status issue is separately actionable. Current `findPdfText()` runs six concurrent page inspections through `Promise.all`, increments progress in each inspection's `finally`, and does not stop pending sibling callbacks when one rejects. The viewer accepts those callbacks without checking whether the request has already failed. A late progress callback can therefore overwrite the terminal error; six attempted pages is consistent with the owner's observed status, but that exact device timing is not yet reproduced. Guard all result/progress/error publication by active request identity and terminal state, including sibling work from the same failed request. Stop further scheduling on failure and clean up outstanding work without delaying error presentation. Keep attempts/completion labels honest; a failed extraction is not a successfully searched page. Use controlled deferred promises to test the failure-then-late-progress and failure-then-retry sequences deterministically, not timing sleeps.

### 5. Reuse primitives and prove the actual hosts

Reuse `BaseButton`, `IconButton` and established icons, existing menu/disclosure patterns, `PanelSurface`, `DialogShell`, `HorizontalResizeHandle`, and `createScrollAffordanceAttachment` as appropriate. Inspect their current APIs before extraction. Reader-specific orchestration belongs in the shared reader/control composition; do not duplicate toolbar and tool state in the sheet route and each annotation host or wrap collection UI around unrelated document navigation.

Reuse `Organisms/ReferenceProof/SelfHostedSrdViewer` for compact/expanded control review and `MixedSourceStates` for external/stale/unavailable regressions. Existing sandbox controls or a deterministic injected loader can expose late errors without multiplying stories. Add a distinct error story only when it cannot be reached practically from those sandboxes. No Storybook play functions.

The pre-rollout proof must also exercise both actual sheet invocation and annotation-draft invocation, using an opt-in proof switch if needed so unapproved layout changes do not silently propagate. Share the trial components, not a bespoke mock. The gate reviews physical-phone rendering/Find, keyboard space, return behavior, and reading-space trade-offs before enabling normal entry points. [verify.md](verify.md) owns exact interactions and evidence. A separate final gate approves integrated rollout.

**Historical trial composition (removed at rollout):** `readerProof=bl-082` enables the shared `ReferenceReaderLayout` in sheet and annotation hosts. It composes existing buttons, resize handles, and scroll-affordance tracking around shared Find/outline/page/document snippets; PDF state and worker ownership stay in `ReferencePdfViewer`. `DialogShell` supplies an opt-in bare workspace that switches native modal/non-modal presentation without remounting the reader; embedded annotation readers instead use a fill-available-space option in their existing shell. Visual-viewport sizing applies only to the trial workspace/embedded-reader mode. The current sheet normally routes field-note entry through `SmallEditDialog`; append `annotationHost=field` during the proof to exercise the retained standalone `FieldAnnotationControl` against real field bindings. This temporary routing switch is not a new product preference and is removed at rollout. Compatibility/error corrections are shared by old and trial layouts; only the new presentation awaits approval.

**Approved rollout (2026-10-09):** After explicit owner approval, `ReferenceReaderLayout` is the only presentation used by `ReferencePdfViewer` in sheet, piecewise-note, standalone-note, and story hosts. Remove `readerProof`, the `refined` branch, the forced `annotationHost` override, and nested fixed viewport heights. Retain standalone-note review in its existing component story; ordinary app regressions exercise the real piecewise host. The owner confirms iPhone 16 Pro Max with the latest installed Safari, Firefox, and Chrome and cannot provide physical Android testing. Android remains a required functioning platform but an acknowledged verification gap owned by BL-072; exact app versions and the oldest supported phone boundary remain unestablished. This is an explicit evidence exception, not a fallback-only support reduction. Final integrated approval is still separate.

## Risks / Trade-offs

**Rollout regression correction (2026-10-09):** WebKit accepted CSS anchors but placed the shared More menu offscreen when invoked from the fixed reader over a deeply scrolled sheet. Extend shared `MenuButton` with a one-time open-placement check and its viewport-edge fallback when native placement is outside viewport bounds, resetting on close. Preserve native dismissal and avoid browser sniffing or continuous scroll measurement. The existing application case now asserts viewport reachability and Escape/reopen behavior. See the [platform-native primitives decision](../../../../docs/decisions/2026-07-17-prefer-platform-native-ui-primitives.md). The mobile continuous-scroll assertion now checks the always-visible page indicator rather than a deliberately undisclosed page input.

- **Compatibility diagnosis remains uncertain** → Capture device/version and failure-stage evidence; capability-removal tests are a targeted regression tool, not a substitute for real iOS.
- **Tools replace visible PDF content on phones** → Keep one-step return and search state; review this trade-off physically before propagation.
- **Responsive focus/modal changes lose drafts or positions** → Keep host ownership explicit; test resizing and both annotation hosts, avoiding nested dialogs and remounts.
- **Extra compatibility code impacts loading or scrolling** → Measure assets and run full browser/performance gates when the PDF build/dependency boundary changes; no speculative compositor CSS.
- **Older whiteout report drives redundant changes** → Start from recorded BL-084 approval, regression-check open and closed states, and fix only reproduced fallout.

## Migration Plan

No data migration. Build the opt-in shared proof and compatibility experiment, obtain explicit approval, then roll out the accepted controls to all current reader hosts and remove temporary switches. Keep the existing browser fallback and desktop behavior during the transition. UI rollback does not require rolling back a separately verified compatibility correction.

Amend the existing viewer ADR with the accepted compact presentation, focus ownership, and compatibility strategy, updating Last reviewed/Latest refinement and explicitly superseding the old stacked-phone-tools rule. A separate ADR is unnecessary unless the compatibility investigation introduces a materially distinct dependency/architecture decision. Follow-ups remain in the backlog; BL-072 owns final multi-system/browser-platform rehearsal, not this change's immediate phone acceptance.

## Open Questions and Proof Decisions

- **Resolved by owner:** affected device and reported OS, all-three-browser failure on that phone versus desktop success, required current iOS/Android support, and broad older-device compatibility as a best-effort goal. No further pre-apply product answer is required.
- **Remaining evidence after approved rollout:** exact physical runtime capabilities/failing stack and numeric browser versions, physical Android coverage, and practical oldest supported versions. Local build identities and controlled missing-capability behavior are recorded in verify.md; the owner reports successful iPhone review. On 2026-10-09 the owner explicitly accepted the unavailable Android evidence gap for rollout; BL-072 owns further physical matrix evidence without weakening required functionality.
- **Recommended, proof-adjustable:** persistent compact controls; independent Find/Outline; tools temporarily replacing the document; container-based threshold; no scroll auto-hide. Refine dimensions, labels, and control placement with the owner rather than fixing them in the behavioral spec.
- **Compatibility choice:** test the pinned supported build path first; if it does not suffice, present the smallest evidence-backed alternative before broad changes.
